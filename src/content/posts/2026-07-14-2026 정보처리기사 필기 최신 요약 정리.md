정보처리기사는 국가기술자격 중 IT 분야에서 가장 널리 취득하는 자격증으로, 소프트웨어 개발 전반의 이론을 폭넓게 다룬다. 필기는 객관식 5과목(과목당 20문항, 총 100문항)으로 구성되며, 과목당 40점 이상 + 전 과목 평균 60점 이상이면 합격이다. 이 글은 단순히 용어를 나열하는 수준을 넘어서, "왜 이 개념이 필요한가", "실제로 어떻게 계산/적용하는가"까지 예제와 함께 풀어써서 별도 교재 없이 이 글만으로도 개념을 완전히 이해할 수 있도록 구성했다.

> 목표: 다른 책이나 강의 없이 이 글만 정독해도 5과목의 핵심 개념, 계산 방법, 코드 트레이싱까지 스스로 할 수 있게 한다.

## 1. 시험 개요 및 합격 전략

### 1-1. 시험 구성

| 항목 | 내용 |
| --- | --- |
| 시행 기관 | 한국산업인력공단(Q-net) |
| 응시 자격 | 제한 없음(관련 학과·경력 무관, 누구나 응시 가능) |
| 필기 방식 | CBT(컴퓨터 기반 시험), 과목당 20문항 총 100문항, 100분 |
| 합격 기준 | 과목당 40점 이상 & 전 과목 평균 60점 이상 |
| 실기 | 필기 합격 후 응시, 통합 코딩형+서술형 문제 출제 |
| 필기 면제 기간 | 필기 합격일로부터 2년간 실기 응시 가능(그 기간 안에는 필기 재응시 불필요) |
| 연간 시행 횟수 | CBT 방식이라 상시(수시)로 회차가 여러 번 진행되며 접수 후 원하는 날짜에 응시 가능한 경우가 많음 |

과목당 40점 커트라인이 있다는 점이 중요하다. 전체 평균이 60점을 넘어도 한 과목이라도 40점 미만이면 과락으로 불합격 처리된다. 따라서 "잘하는 과목으로 못하는 과목을 커버"하는 전략은 통하지 않으며, 5과목 모두 최소 40점 이상을 확보하는 것이 최우선 목표가 되어야 한다.

### 1-2. 과목 구성

1. 소프트웨어 설계 — 요구사항 분석, UML, 아키텍처/디자인 패턴, 모듈 설계
2. 소프트웨어 개발 — 자료구조, 알고리즘, 테스트, 형상관리
3. 데이터베이스 구축 — 정규화, SQL, 트랜잭션, 인덱스
4. 프로그래밍 언어 활용 — C/Java/Python, 운영체제, 네트워크
5. 정보시스템 구축관리 — 개발 방법론, 프로젝트 관리, 신기술, 보안

과목 이름만 보면 서로 독립적으로 보이지만 실제로는 내용이 겹치는 부분이 많다. 예를 들어 "테스트"는 2과목(소프트웨어 개발)에서 주로 다루지만 1과목의 "요구사항 검증"과도 연결되고, "보안"은 5과목에서 다루지만 4과목의 "시큐어 코딩"·3과목의 "무결성 제약조건"과도 맞닿아 있다. 이렇게 과목을 넘나드는 연결고리를 파악해두면 응용문제에 강해진다.

### 1-3. 공부 전략

- **암기 과목(1·3·5과목)** 은 용어 정의와 특징 비교표 위주로 반복 회독한다. 단순 암기보다는 "왜 이런 개념이 필요한가"를 한 문장으로 설명할 수 있을 정도로 이해하면 응용 문제에도 대응이 된다.
- **계산/코드 과목(2·4과목)** 은 직접 손으로 트레이싱하며 풀어야 한다. 특히 프로그래밍 언어 활용의 C/Java/Python 코드 문제는 눈으로만 봐서는 틀리기 쉽다. 변수 값 변화를 표로 그려가며 한 줄씩 실행 결과를 추적하는 습관을 들이자.
- 기출문제 회독 비중을 70% 이상으로 두는 것이 효율적이다. 최근 몇 년간 과목 개편 이후 기출 재출제 비율이 높고, 지문이 거의 동일하게 반복되는 문제도 상당수다.
- 헷갈리는 용어는 반의어/유사어 쌍으로 묶어서 외우면 오래 간다(예: 응집도↔결합도, 정규화↔반정규화, 화이트박스↔블랙박스, 상향식↔하향식 통합).
- **회독 순서 추천**: 3과목(DB) → 1과목(설계) → 5과목(구축관리) → 2과목(개발) → 4과목(언어활용) 순으로 암기 과목을 먼저 끝내고, 코드/계산 문제가 많은 과목을 뒤에 배치해 감을 유지한 채 시험장에 들어가는 방식이 흔히 추천된다.
- **일 평균 학습 시간**: 비전공자 기준 하루 2~3시간씩 2~3주, 전공자·실무자는 1~2주 집중 회독으로도 충분한 경우가 많다. 다만 프로그래밍 언어 활용 과목은 코드 경험이 없다면 별도로 시간을 더 투자해야 한다.
- **오답노트 활용**: 틀린 문제를 과목별로 모아두고, 오답의 "함정 포인트"(예: 유사 용어 바꿔치기, 순서 뒤바꾸기)를 짧게 메모해두면 반복 회독 시간이 크게 줄어든다.
- **4주 학습 계획 예시**(비전공자 기준):
  - 1주차: 3과목(DB) + 1과목(설계) 이론 1회독, 매일 기출 20문항
  - 2주차: 5과목(구축관리) 이론 1회독 + 1~3과목 기출 2회독
  - 3주차: 2과목(개발) + 4과목(언어활용) 이론 1회독, 코드 트레이싱 집중 연습
  - 4주차: 5과목 전체 기출 3회독 + 오답노트 집중 복습 + 실전 모의고사

## 2. 1과목: 소프트웨어 설계

### 2-1. 요구사항 분석

요구사항 분석이 왜 중요한지부터 짚어보자. 개발 초기에 요구사항을 잘못 정의하면, 이후 설계·구현·테스트 단계에서 발견되는 결함보다 훨씬 큰 비용(때로는 수십 배)이 든다. 그래서 이 과목의 첫 챕터는 항상 "요구사항을 어떻게 정확히 뽑아내고 검증하는가"에서 출발한다.

- **기능적 요구사항**: 시스템이 무엇을 해야 하는가 (입출력, 처리 로직, 계산 규칙, 데이터 처리 절차). 예: "회원가입 시 이메일 중복을 검사해야 한다."
- **비기능적 요구사항**: 성능, 보안, 사용성, 신뢰성, 이식성, 효율성 등 품질 속성. 흔히 "~해야 한다"보다 "얼마나 빠르게/안전하게"처럼 정량적 기준으로 표현된다. 예: "응답 시간은 2초 이내여야 한다."
- **요구사항 검증 방법**: 요구사항 검토(리뷰, 여러 이해관계자가 문서를 함께 확인), 프로토타이핑(시제품을 만들어 직접 사용해보며 확인), 모델 검증(정형 명세 기법으로 시뮬레이션·수학적 증명), 인수 테스트(실사용자가 실제 업무 시나리오로 검증)
- **요구공학(Requirements Engineering) 프로세스**: 도출(Elicitation) → 분석(Analysis) → 명세(Specification) → 확인(Validation) 순서로 진행되며, 각 단계는 반복적으로 순환한다. 도출 단계에서 놓친 요구사항이 분석 단계에서 발견되면 다시 도출로 돌아가는 식이다.
- **요구사항 도출 기법**: 인터뷰(1:1 심층 질의), 설문(다수 대상 정량 데이터 수집), 브레인스토밍(자유로운 아이디어 발산), 워크숍(이해관계자 합동 회의), 유스케이스 작성, 프로토타이핑
- **정형 명세 기법**: 수학적 기호와 표기법(Z 명세, VDM)으로 요구사항을 정확하게 표현 — 모호함이 없지만 작성 난이도가 높아 실무에서는 안전 필수 시스템(항공, 의료 등)에 주로 사용
- **비정형 명세 기법**: 자연어 기반 서술 방식(사용자 스토리, 유스케이스 명세서) — 이해하기 쉽지만 사람마다 해석이 달라질 수 있는 모호성이 존재

**시험 함정 포인트**: "기능적 요구사항 = 무엇을(What)", "비기능적 요구사항 = 어떻게/얼마나(How well)"로 구분해서 외우면 지문에서 예시가 나와도 바로 분류할 수 있다. 예를 들어 "로그인 기능이 있어야 한다"는 기능적, "로그인은 0.5초 이내에 처리되어야 한다"는 비기능적이다.

### 2-2. UML(Unified Modeling Language)

UML은 소프트웨어 구조와 동작을 표준화된 그림으로 표현하기 위한 모델링 언어다. 다이어그램은 크게 **구조적 다이어그램**(정적인 구조, "무엇으로 구성되어 있는가")과 **행위 다이어그램**(동적인 동작, "어떻게 동작하는가")으로 나뉜다.

| 구분 | 종류 |
| --- | --- |
| 구조적 다이어그램 | 클래스, 객체, 컴포넌트, 배치(Deployment), 복합체 구조, 패키지 |
| 행위 다이어그램 | 유스케이스, 시퀀스, 활동(Activity), 상태(State), 협력(Communication), 타이밍 |

- **유스케이스 다이어그램**: 사용자(액터)와 시스템 기능(유스케이스) 간의 상호작용을 표현. 관계에는 include(포함, 기본 유스케이스 실행 시 항상 함께 실행되는 하위 기능 — 예: "주문하기"는 항상 "재고 확인하기"를 포함), extend(확장, 조건에 따라 선택적으로 실행되는 기능 — 예: "결제하기"에 "쿠폰 적용하기"가 조건부로 확장), generalization(일반화, 상속 관계 — 예: "회원 로그인"과 "관리자 로그인"이 "로그인"을 일반화)
- **시퀀스 다이어그램**: 객체 간 메시지 교환을 시간 순서로 표현하는 대표적인 행위 다이어그램. 구성 요소는 Lifeline(객체의 생명선, 세로 점선), Activation(메시지 처리 중임을 나타내는 세로 막대), Message(객체 간 호출, 동기 메시지는 실선 화살표, 비동기 메시지는 열린 화살표로 구분). 예를 들어 "고객 → 주문시스템 → 재고시스템 → 결제시스템" 순서로 메시지가 오가는 흐름을 그대로 시간 축을 따라 그린다.
- **클래스 다이어그램 관계**: 연관(Association, 단순 참조 관계), 집합(Aggregation, 부분이 전체 없이도 독립적으로 존재 가능 — 예: "학과"와 "학생", 학과가 없어져도 학생은 존재), 합성(Composition, 부분이 전체에 강하게 종속 — 예: "집"과 "방", 집이 없어지면 방도 없어짐), 일반화(상속), 의존(Dependency, 일시적으로 사용하는 약한 관계)
- **연관 관계 다중성 표기**: 1(정확히 하나), 0..1(없거나 하나), 0..*(0개 이상), 1..*(1개 이상) 등으로 두 클래스 간 관계 개수를 표현하며, 시험에서 다중성 기호를 그림에 대입해 해석하는 문제가 자주 나온다.
- **상태 다이어그램**: 하나의 객체가 생명주기 동안 가지는 상태와 상태 전이(Transition)를 표현, 이벤트에 의해 상태가 바뀜. 예: 주문 객체가 "대기중 → 결제완료 → 배송중 → 배송완료" 순서로 상태가 전이되는 흐름을 그림으로 표현.
- **활동 다이어그램**: 업무 흐름이나 알고리즘의 절차적 흐름을 분기(Decision, 조건에 따른 갈림길), 병행(Fork/Join, 동시에 진행되다가 다시 합쳐지는 흐름)까지 포함해 표현하며, 순서도(Flowchart)와 유사하지만 UML 표준 표기법을 따른다.

### 2-3. 소프트웨어 아키텍처 패턴

아키텍처 패턴은 "시스템 전체를 어떤 구조로 나눌 것인가"에 대한 검증된 해법이다. 하나의 시스템 안에서도 여러 패턴이 혼합되어 사용되는 경우가 흔하다.

| 패턴 | 특징 |
| --- | --- |
| 계층형(Layered) | Presentation-Business-Persistence 등 계층 분리, 유지보수 용이, 상위 계층은 하위 계층에만 의존(하위 계층은 상위 계층을 몰라야 함) |
| 클라이언트-서버 | 서비스 요청자/제공자 구조, 다수의 클라이언트가 하나의 서버에 요청 |
| 파이프-필터 | 데이터 스트림을 필터가 순차 처리(예: 유닉스 파이프 `cat file`→`grep word`→`sort`), 각 필터는 독립적이고 재사용 가능하지만 전체 흐름이 순차적이라 병렬화가 어려움 |
| MVC | Model-View-Controller, 관심사 분리의 대표 사례. Controller가 사용자 입력을 받아 Model을 갱신하고, Model의 변경사항을 View가 반영(Observer 패턴과 연결됨) |
| 브로커(Broker) | 분산 시스템에서 컴포넌트 간 통신 중개, 클라이언트는 브로커를 통해서만 서버와 통신하므로 클라이언트와 서버가 서로의 위치를 몰라도 됨 |
| 이벤트 기반 | 이벤트 발생-구독 방식, 느슨한 결합, 이벤트 발행자와 구독자가 서로를 모름(간접적으로만 연결) |
| 마이크로커널(Microkernel) | 핵심 기능만 커널(Core)에 두고 나머지는 플러그인 형태로 확장(OS 커널, IDE 플러그인 구조가 대표적) |
| 저장소(Repository) | 중앙 데이터 저장소를 여러 컴포넌트가 공유(블랙보드 아키텍처와 유사), 컴포넌트들은 저장소를 통해서만 간접적으로 소통 |

- **아키텍처 품질 속성**: 성능, 보안, 가용성, 사용성, 시험 가능성(Testability), 변경 용이성 등은 아키텍처 설계 초기에 결정되며 이후 변경 비용이 매우 크다. 예를 들어 나중에 "보안을 강화해야 한다"고 해서 아키텍처를 뒤엎는 것은 비용이 막대하므로, 초기 설계 단계에서 품질 속성 우선순위를 명확히 정해야 한다.
- **아키텍처 설계 원칙**: 관심사의 분리(SoC, 서로 다른 책임을 다른 모듈로 분리), 모듈화, 정보 은닉(Information Hiding, 내부 구현을 숨기고 인터페이스만 노출), 추상화 수준 관리

### 2-4. 디자인 패턴 (GoF 23가지)

GoF(Gang of Four) 패턴은 반복되는 설계 문제에 대한 검증된 해법을 정리한 것으로, 생성(Creational), 구조(Structural), 행위(Behavioral) 3가지로 분류된다.

| 분류 | 대표 패턴 |
| --- | --- |
| 생성 패턴 | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| 구조 패턴 | Adapter, Bridge, Composite, Decorator, Facade, Flyweight, Proxy |
| 행위 패턴 | Observer, Strategy, Command, State, Template Method, Iterator, Visitor, Mediator, Chain of Responsibility, Memento, Interpreter |

각 패턴이 "무엇을 해결하는가"를 짝지어 이해하면 헷갈리지 않는다. 아래는 자주 출제되는 패턴을 의사코드 수준으로 풀어 쓴 설명이다.

#### 생성 패턴

- **Singleton**: 인스턴스를 하나만 생성, 전역 접근점 제공 (시험 최다 출제). 설정 객체, 커넥션 풀, 로거 등에 사용. 핵심은 생성자를 private으로 막고, 클래스 내부에서 유일한 인스턴스를 static으로 관리하며 `getInstance()` 같은 정적 메서드로만 접근을 허용한다는 점이다.
- **Factory Method**: 객체 생성을 서브클래스에 위임해 생성 로직과 사용 로직을 분리. 예를 들어 `AnimalFactory`가 있고, `DogFactory`/`CatFactory`가 이를 상속받아 각자 다른 종류의 `Animal` 객체를 생성하는 식이다. 클라이언트 코드는 구체적인 클래스를 몰라도 된다.
- **Abstract Factory**: 관련 객체군(제품군)을 일관성 있게 생성하는 인터페이스 제공 (예: OS별 UI 위젯 세트 생성 — Windows용 Button/Checkbox 세트, Mac용 Button/Checkbox 세트를 각각 일관되게 생성)
- **Builder**: 복잡한 객체를 단계별로 조립해 생성, 동일한 조립 과정으로 다른 표현 결과를 만들 수 있음(예: `PizzaBuilder`가 도우 → 소스 → 토핑 순서로 조립하되, 토핑 종류만 바꾸면 다른 피자가 나옴)
- **Prototype**: 기존 객체를 복제(clone)해서 새 객체를 생성, 생성 비용이 큰 객체를 매번 새로 만들지 않고 복제로 대체

#### 구조 패턴

- **Adapter**: 호환되지 않는 인터페이스를 클라이언트가 기대하는 형태로 변환(기존 코드 재사용에 유용). 예: 220V 플러그를 110V 콘센트에 꽂기 위한 어댑터처럼, 기존 클래스를 감싸서 원하는 인터페이스로 노출한다.
- **Bridge**: 추상화와 구현을 분리해 각각 독립적으로 확장 가능하게 함(예: 도형(추상화)과 색상(구현)을 분리해 도형×색상 조합이 늘어나도 클래스 폭발을 방지)
- **Composite**: 개별 객체와 복합 객체를 동일하게 다루도록 트리 구조로 구성(예: 파일과 폴더를 같은 인터페이스로 다뤄서 폴더 안에 파일과 폴더가 섞여 있어도 동일하게 처리)
- **Decorator**: 객체에 동적으로 새로운 책임(기능)을 추가, 상속 대신 위임(Composition) 사용(예: 커피에 우유·시럽을 겹겹이 감싸서 가격과 기능을 추가하는 방식)
- **Facade**: 복잡한 서브시스템을 단순한 하나의 인터페이스로 감싸 제공(예: 컴파일러 내부의 여러 단계(어휘분석, 구문분석, 코드생성)를 `compile()` 하나로 감싸 제공)
- **Flyweight**: 자주 반복되는 객체를 공유해서 메모리 사용을 줄임(예: 문서 편집기에서 같은 글자 폰트 객체를 공유)
- **Proxy**: 실제 객체에 대한 접근을 대리자가 제어(권한 검사, 지연 로딩, 원격 접근 등에 사용)

#### 행위 패턴

- **Observer**: 1:N 의존 관계, 상태 변화 시 등록된 옵저버에 자동 통지 (이벤트 리스너, MVC의 View 갱신이 대표적인 사례)
- **Strategy**: 알고리즘군을 캡슐화해 런타임에 교체 가능하게 함 (정렬 전략, 결제 방식 교체 등 — 예: `PaymentStrategy` 인터페이스를 두고 신용카드/카카오페이/계좌이체를 각각 구현체로 교체)
- **Command**: 요청 자체를 객체로 캡슐화해 실행 취소(Undo), 큐잉, 로깅 등을 가능하게 함
- **State**: 객체의 상태에 따라 행동이 달라지는 경우 상태를 객체로 분리해 관리(if-else 분기 폭증을 방지)
- **Template Method**: 상위 클래스에서 알고리즘의 골격을 정의하고, 세부 단계는 하위 클래스가 구현(예: `상위클래스.process()`가 `준비() → 실행() → 마무리()` 순서를 고정하고, 각 단계의 세부 구현만 하위 클래스가 오버라이드)
- **Iterator**: 컬렉션의 내부 구조를 노출하지 않고 순차적으로 접근하는 방법 제공
- **Mediator**: 여러 객체 간의 복잡한 상호작용을 중재자 객체 하나로 집중시켜 결합도를 낮춤
- **Chain of Responsibility**: 요청을 처리할 객체를 체인 형태로 연결해, 앞 객체가 처리하지 못하면 다음 객체로 넘김(예: 결재 승인 단계별 처리)

### 2-5. 모듈 설계 - 응집도와 결합도

시험에서 가장 자주 나오는 개념 중 하나로, 응집도는 높을수록, 결합도는 낮을수록 좋은 설계다. 좋은 모듈은 "하나의 역할만 충실히 수행"하면서 "다른 모듈과는 최소한으로만 연결"되어야 한다. 왜 그런지 생각해보면, 응집도가 높으면 모듈 하나의 기능을 이해/수정하기 쉽고, 결합도가 낮으면 한 모듈을 고쳐도 다른 모듈에 영향을 덜 준다.

#### 응집도 (강함 → 약함 순서, 암기: 기순통절 논시우)

1. **기능적 응집도(Functional)**: 모듈 내 모든 요소가 단 하나의 기능 수행을 위해 긴밀히 협력(가장 이상적). 예: "세금 계산 모듈"이 오직 세금 계산과 관련된 코드만 포함.
2. **순차적 응집도(Sequential)**: 한 요소의 출력이 다음 요소의 입력으로 사용됨. 예: 파일을 읽고(출력=데이터) 그 데이터를 정렬하는(입력=데이터) 흐름.
3. **통신적 응집도(Communicational)**: 동일한 입력/출력 데이터를 사용하는 요소들이 모여 있음. 예: 같은 고객 데이터를 가지고 "주소 갱신"과 "이메일 발송"을 함께 수행.
4. **절차적 응집도(Procedural)**: 특정 순서로 실행되어야 하는 요소들의 집합이지만 데이터 관련성은 약함.
5. **시간적 응집도(Temporal)**: 특정 시점에 함께 실행되어야 하는 요소들의 집합(초기화 루틴, 프로그램 종료 처리 등).
6. **논리적 응집도(Logical)**: 유사한 성격/기능을 논리적으로만 묶어놓음(실제 관련성은 약함). 예: "모든 입력 처리 함수"를 한 모듈에 몰아넣었지만 각 함수는 서로 관련이 없음.
7. **우연적 응집도(Coincidental)**: 서로 관련 없는 요소들이 우연히 하나의 모듈에 묶임(가장 나쁨). 예: 아무 이유 없이 코드 조각들을 한 파일에 모아놓음.

#### 결합도 (약함 → 강함 순서, 암기: 자스제외공내공)

1. **자료 결합도(Data)**: 필요한 데이터(매개변수)만 전달, 가장 바람직한 결합. 예: `calculateTax(income)`처럼 딱 필요한 값만 넘김.
2. **스탬프 결합도(Stamp)**: 자료구조(레코드, 객체) 전체를 전달해 불필요한 데이터까지 노출. 예: `calculateTax(customerObject)`처럼 고객 객체 전체를 넘기지만 실제로는 income 필드만 필요.
3. **제어 결합도(Control)**: 제어 플래그·스위치 값을 전달해 상대 모듈의 흐름을 제어. 예: `process(flag)`에서 flag 값에 따라 내부 분기가 완전히 달라짐.
4. **외부 결합도(External)**: 외부에서 정의한 데이터 형식·프로토콜에 의존. 예: 특정 파일 포맷이나 통신 프로토콜 규격에 강하게 의존.
5. **공통 결합도(Common)**: 전역 변수를 여러 모듈이 공유(부작용 추적 어려움). 한 모듈이 전역 변수를 변경하면 다른 모듈이 예상치 못한 동작을 할 수 있음.
6. **내용 결합도(Content)**: 한 모듈이 다른 모듈의 내부 로직·데이터를 직접 참조/변경(가장 나쁨). 예: 모듈 A가 모듈 B의 내부 변수를 직접 수정.

**함정 포인트**: 응집도는 "강함(좋음)"이 위, 결합도는 "약함(좋음)"이 위로 시작하는데, 문제에서 순서를 거꾸로 제시하고 "옳은 것은?"이라고 물어보는 경우가 많다. 반드시 "응집도는 강한 게 좋다 → 1번이 기능적", "결합도는 약한 게 좋다 → 1번이 자료"라는 시작점을 확실히 기억하자.

### 2-6. 인터페이스 설계

- **미들웨어**: RPC(원격 프로시저 호출, 다른 컴퓨터의 함수를 로컬 함수처럼 호출), MOM(Message Oriented Middleware, 메시지 큐 기반 비동기 통신 — 송신자와 수신자가 동시에 접속해 있지 않아도 됨), TP-Monitor(트랜잭션 처리 감시, 다수의 트랜잭션을 안정적으로 관리), WAS(Web Application Server), ORB(객체 요청 브로커, CORBA 표준), DB 미들웨어
- **인터페이스 명세**: 인터페이스 목록, 상세 기능 명세, 데이터 항목·형식 정의, 오류 코드 및 예외 처리 규칙
- **연계 방식**: EAI(Enterprise Application Integration, 기업 내 애플리케이션 통합), ESB(Enterprise Service Bus, 서비스 중심의 느슨한 통합 버스 — EAI보다 표준화되고 유연한 방식)
- **EAI 구축 유형**: Point-to-Point(1:1 직접 연결, 시스템이 늘어날수록 연결선이 기하급수적으로 증가), Hub & Spoke(중앙 허브를 거쳐 연결, 허브 장애 시 전체 영향), Message Bus(ESB 방식, 버스에 메시지를 발행하고 필요한 시스템이 구독), Hybrid(허브+메시지버스 혼합)
- **인터페이스 보안**: 데이터 전송 구간 암호화(TLS/SSL), API 키·토큰 기반 인증, 접근 로그 감사
- **REST vs SOAP**: REST는 HTTP 메서드(GET/POST/PUT/DELETE)를 활용한 경량 아키텍처 스타일로 JSON을 주로 사용하며, SOAP는 XML 기반의 무겁지만 엄격한 프로토콜(WSDL로 인터페이스 명세, 보안·트랜잭션 표준이 강함)로 금융권 레거시 시스템에서 자주 쓰인다.

## 3. 2과목: 소프트웨어 개발

### 3-1. 자료구조

| 구분 | 종류 | 특징 |
| --- | --- | --- |
| 선형 구조 | 배열, 리스트, 스택, 큐, 데크 | 순서가 있는 데이터 |
| 비선형 구조 | 트리, 그래프 | 계층/관계형 데이터 |

- **배열(Array)**: 고정 크기, 인덱스로 O(1) 접근이 가능하지만 삽입/삭제 시 데이터 이동 비용 발생(중간에 삽입하려면 뒤 요소들을 한 칸씩 밀어야 함)
- **연결 리스트(Linked List)**: 노드가 다음 노드를 가리키는 포인터로 연결, 삽입/삭제는 빠르지만(포인터만 바꾸면 되므로 O(1)) 임의 접근은 느림(맨 앞부터 순서대로 따라가야 하므로 O(n))
- **스택(Stack)**: LIFO(Last In First Out), 재귀 호출·수식 계산(중위→후위 표기법 변환, 후위 표기법 계산)에 사용. 괄호 검사, 브라우저 뒤로가기 기능 구현에도 활용

**후위 표기법 계산 예제**: 후위 표기식 `3 4 + 5 *`를 스택으로 계산하는 과정을 직접 따라가 보자.

```text
1. '3'을 만나면 스택에 push → 스택: [3]
2. '4'를 만나면 스택에 push → 스택: [3, 4]
3. '+'를 만나면 스택에서 두 개를 pop(4, 3)해서 3+4=7을 계산 후 push → 스택: [7]
4. '5'를 만나면 스택에 push → 스택: [7, 5]
5. '*'를 만나면 두 개를 pop(5, 7)해서 7*5=35를 계산 후 push → 스택: [35]
6. 스택에 남은 값이 최종 결과 → 35
```

- **큐(Queue)**: FIFO(First In First Out), 버퍼링·프로세스 스케줄링에 사용. 원형 큐(Circular Queue)는 배열 기반 큐의 오버플로우 문제를 해결(rear가 배열 끝에 도달하면 다시 앞으로 순환)
- **데크(Deque)**: 양쪽 끝에서 삽입/삭제가 모두 가능한 구조, 스택과 큐의 특성을 모두 가짐
- **트리(Tree)**: 루트에서 리프까지 계층적 구조, 사이클이 없는 그래프의 특수한 형태. 이진 트리, 이진 탐색 트리(BST, 왼쪽 자식은 부모보다 작고 오른쪽 자식은 부모보다 큼), 균형 트리(AVL, 레드-블랙 트리)로 확장

**트리 순회 예제**: 아래와 같은 이진 트리가 있다고 하자.

```text
        A
       / \
      B   C
     / \
    D   E
```

- 전위 순회(Preorder, 루트→좌→우): `A B D E C`
- 중위 순회(Inorder, 좌→루트→우): `D B E A C`
- 후위 순회(Postorder, 좌→우→루트): `D E B C A`

세 순회 방식 모두 "루트를 언제 방문하느냐"만 다르다는 점을 기억하면 헷갈리지 않는다(전위=먼저, 중위=중간, 후위=마지막).

- **그래프 탐색**: 너비 우선 탐색(BFS, 큐 사용, 가까운 노드부터 차례로 방문하므로 최단 경로 탐색에 유리), 깊이 우선 탐색(DFS, 스택/재귀 사용, 한 방향으로 끝까지 파고드는 방식이라 백트래킹에 유리)
- **해시 테이블(Hash Table)**: 키를 해시 함수로 변환해 O(1) 평균 접근 속도 제공. 해시 충돌(서로 다른 키가 같은 해시값을 갖는 경우) 해결법으로 체이닝(Chaining, 같은 버킷에 연결 리스트로 연결), 개방 주소법(Open Addressing, 충돌 시 다른 빈 자리를 탐색)이 있음

### 3-2. 정렬 알고리즘 시간 복잡도

| 알고리즘 | 평균 | 최선 | 최악 | 특징 |
| --- | --- | --- | --- | --- |
| 버블 정렬 | O(n²) | O(n²) | O(n²) | 인접 요소 비교/교환 반복, 구현 단순 |
| 선택 정렬 | O(n²) | O(n²) | O(n²) | 매 회전마다 최솟값을 찾아 앞으로 이동 |
| 삽입 정렬 | O(n²) | O(n) | O(n²) | 이미 정렬된 부분에 새 요소를 적절한 위치에 삽입 |
| 퀵 정렬 | O(n log n) | O(n log n) | O(n²) | 피벗 기준 분할 정복, 평균적으로 가장 빠름 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n log n) | 분할 정복 + 병합, 안정 정렬, 추가 메모리 필요 |
| 힙 정렬 | O(n log n) | O(n log n) | O(n log n) | 완전 이진 트리(힙) 구조 이용, 추가 메모리 불필요 |
| 셸 정렬 | O(n^1.5) | O(n log n) | O(n²) | 삽입 정렬을 간격(gap)을 두고 개선 |

퀵 정렬은 평균은 빠르지만 이미 정렬된 데이터에서 피벗 선택이 나쁘면 최악의 경우 O(n²)로 저하된다는 점이 자주 출제된다. 병합 정렬은 항상 O(n log n)을 보장하지만 별도의 배열 공간이 필요하다는 점도 함께 기억해두자.

**버블 정렬 트레이싱 예제**: 배열 `[5, 2, 4, 1]`을 오름차순으로 버블 정렬하는 과정.

```text
1회전: (5,2)비교→교환 [2,5,4,1] → (5,4)비교→교환 [2,4,5,1] → (5,1)비교→교환 [2,4,1,5]
2회전: (2,4)비교→유지 [2,4,1,5] → (4,1)비교→교환 [2,1,4,5]
3회전: (2,1)비교→교환 [1,2,4,5]
결과: [1, 2, 4, 5]
```

매 회전마다 가장 큰 값이 뒤로 "밀려나는" 방식이라는 점이 버블 정렬의 핵심이다.

### 3-3. 테스트

- **화이트박스 테스트**: 내부 로직/구조를 보고 테스트 (기초 경로 검사, 조건 검사, 루프 검사, 데이터 흐름 검사). 코드 커버리지(구문/분기/조건 커버리지)를 측정하는 데 사용. 기초 경로 검사에서는 사이클로매틱 복잡도(Cyclomatic Complexity)를 계산하는데, 공식은 `V(G) = E - N + 2` (E=간선 수, N=노드 수)이며, 이 값이 곧 테스트해야 할 최소 독립 경로의 수가 된다.
- **블랙박스 테스트**: 입출력만 보고 테스트 (동치 분할, 경계값 분석, 원인-결과 그래프, 오류 예측 검사). 내부 구조를 몰라도 수행 가능. 예를 들어 "1~100 사이 숫자만 입력 가능"이라는 요구사항이 있다면, 경계값 분석은 0, 1, 100, 101처럼 경계에 가까운 값을 집중적으로 테스트하는 기법이다.
- **테스트 레벨**: 단위 테스트(개별 함수/모듈) → 통합 테스트(모듈 간 연동) → 시스템 테스트(전체 시스템) → 인수 테스트(사용자 관점 최종 검증) 순으로 진행되며, V-모델에서는 각 개발 단계와 테스트 단계가 대응된다(요구사항 분석↔인수 테스트, 아키텍처 설계↔시스템 테스트, 상세 설계↔통합 테스트, 구현↔단위 테스트).
- **통합 테스트 방식**: 빅뱅(Big Bang, 전체를 한 번에 통합, 결함 위치 파악이 어려움), 상향식(Bottom-Up, 하위 모듈부터 결합하며 상위 모듈을 대신할 드라이버 필요), 하향식(Top-Down, 상위 모듈부터 결합하며 하위 모듈을 대신할 스텁 필요)
- **테스트 커버리지 기준**: 구문 커버리지(모든 코드 라인 실행), 결정 커버리지(모든 분기의 참/거짓 실행), 조건 커버리지(각 개별 조건의 참/거짓 실행), MC/DC(조건+결정 커버리지 결합, 가장 엄격 — 항공우주 등 안전 필수 시스템에서 요구)
- **테스트 오라클(Test Oracle)**: 테스트 결과가 옳은지 판단하는 기준 — 참 오라클(완전 검증), 샘플링 오라클(일부만 검증), 휴리스틱 오라클(추정 값과 비교)

### 3-4. 형상 관리(Configuration Management)

- 목적: 소프트웨어 변경 이력을 체계적으로 관리해 무결성과 추적성 확보, 여러 개발자가 동시에 작업해도 버전 충돌을 방지
- 4대 활동: 형상 식별(관리 대상 항목 선정), 형상 통제(변경 요청 검토·승인), 형상 감사(기준선 준수 여부 검증), 형상 기록/상태 보고(변경 이력 추적)
- 도구 예시: Git(분산형, 브랜치 관리 강력), SVN(중앙집중형), CVS(SVN 이전 세대 도구)
- **베이스라인(Baseline)**: 공식적으로 승인되어 이후 변경 시 정식 절차를 거쳐야 하는 기준 형상. 요구사항 기준선, 설계 기준선, 제품 기준선 등으로 단계별 관리

### 3-5. 클린 코드 원칙 및 빌드 도구

- 가독성(Readability), 단순성(Simplicity), 의존성 배제(낮은 결합도), 중복 최소화(DRY), 추상화(Abstraction), 일관성 있는 네이밍
- **리팩토링(Refactoring)**: 외부 동작(기능)은 그대로 유지하면서 내부 구조를 개선하는 작업. 코드 스멜(중복 코드, 긴 메서드, 거대한 클래스 등)을 제거하는 것이 목표
- **빌드 자동화 도구**: Ant(XML 기반, 절차적 스크립트), Maven(POM.xml 기반 의존성 관리, 표준화된 빌드 생명주기), Gradle(Groovy/Kotlin DSL, 증분 빌드로 속도 우수)
- **정적 분석 vs 동적 분석**: 정적 분석은 코드를 실행하지 않고 결함을 찾음(체크스타일, PMD — 코드를 읽기만 해서 잠재적 버그·스타일 위반을 탐지), 동적 분석은 실제 실행하며 결함을 찾음(프로파일러, 디버거 — 실행 중 메모리 누수나 실제 값 오류를 탐지)

## 4. 3과목: 데이터베이스 구축

### 4-1. 데이터베이스 설계 단계

```text
요구사항 분석 → 개념적 설계(E-R 다이어그램) → 논리적 설계(정규화, 스키마) → 물리적 설계(저장 구조, 인덱스) → 구현
```

- **개념적 설계**: 요구사항을 E-R(개체-관계) 다이어그램으로 표현, 특정 DBMS에 종속되지 않는 추상적 모델. 예: "학생"과 "과목"이라는 개체가 있고 그 사이에 "수강"이라는 관계가 있다는 것을 그림으로 표현.
- **E-R 다이어그램 구성요소**: 개체(Entity, 사각형 — 예: 학생, 과목), 속성(Attribute, 타원 — 예: 학번, 이름), 관계(Relationship, 마름모 — 예: 수강), 키 속성(밑줄로 표시)
- **논리적 설계**: 특정 데이터 모델(관계형)에 맞춰 스키마로 변환, 정규화를 통해 데이터 중복 제거. 예를 들어 "학생(학번, 이름)"과 "수강(학번, 과목코드, 성적)"처럼 실제 테이블 구조로 변환하는 단계다.
- **물리적 설계**: 저장 장치에 실제로 저장될 방법 결정(인덱스, 파티션, 저장 공간 산정)
- **스키마 3단계**: 외부 스키마(사용자 관점, View — 개별 사용자가 보는 화면 단위), 개념 스키마(전체 논리적 구조 — DB 전체를 아우르는 스키마 하나), 내부 스키마(물리적 저장 구조 — 실제 디스크에 어떻게 저장되는지) — 각 단계를 분리해 두는 이유는 데이터 독립성(하나가 바뀌어도 다른 계층에 영향을 최소화) 확보가 목적이다.

### 4-2. 정규화(Normalization)

정규화는 데이터 중복을 최소화하고 이상 현상(삽입/삭제/갱신 이상)을 방지하기 위한 과정이다. 말로만 들으면 추상적이니, 실제 테이블 예시로 살펴보자.

#### 정규화가 필요한 이유 — 예시 테이블

아래처럼 "수강" 테이블 하나에 모든 정보를 몰아넣었다고 하자.

| 학번 | 이름 | 과목코드 | 과목명 | 담당교수 |
| --- | --- | --- | --- | --- |
| 1001 | 김철수 | CS101 | 자료구조 | 이교수 |
| 1001 | 김철수 | CS102 | 운영체제 | 박교수 |
| 1002 | 이영희 | CS101 | 자료구조 | 이교수 |

이 테이블에는 세 가지 이상 현상이 숨어있다.

- **삽입 이상**: 아직 수강 신청을 하지 않은 새 과목(예: CS103)을 추가하려면, 수강생이 없어도 억지로 학번·이름 정보를 채워야 함(혹은 NULL 처리 필요)
- **삭제 이상**: 김철수가 CS102 수강을 취소해서 그 행을 삭제하면, "CS102 = 운영체제, 담당교수 = 박교수"라는 정보 자체가 통째로 사라짐
- **갱신 이상**: 이교수가 "김교수"로 이름이 바뀌면, "이교수"가 담당하는 모든 행(CS101 관련 행 전체)을 일일이 찾아서 수정해야 하며, 하나라도 놓치면 데이터 불일치 발생

이 문제를 해결하는 과정이 정규화다. 위 테이블을 분해하면:

- `학생(학번, 이름)`
- `과목(과목코드, 과목명, 담당교수)`
- `수강(학번, 과목코드)`

이렇게 분리하면 과목 정보는 "과목" 테이블에 단 한 번만 저장되므로 위의 세 가지 이상 현상이 모두 해결된다.

| 정규형 | 조건 |
| --- | --- |
| 1NF | 모든 속성이 원자값을 가짐(반복 그룹 제거) |
| 2NF | 1NF 만족 + 부분 함수 종속 제거 (기본키 전체에 완전 함수 종속) |
| 3NF | 2NF 만족 + 이행 함수 종속 제거 (A→B→C 형태의 간접 종속 제거) |
| BCNF | 3NF 만족 + 모든 결정자가 후보키 (강한 정규형) |
| 4NF | BCNF 만족 + 다치 종속(Multi-valued Dependency) 제거 |
| 5NF | 4NF 만족 + 조인 종속(Join Dependency) 제거 |

- **1NF 위반 예시**: 한 학생이 여러 취미를 가질 때 `취미` 컬럼에 "독서, 영화, 게임"처럼 여러 값을 콤마로 넣는 것은 원자값이 아니므로 1NF 위반이다. 이 경우 취미를 별도 행/테이블로 분리해야 한다.
- **2NF 위반 예시**: 위의 "수강(학번, 과목코드, 이름, 과목명)"에서 기본키는 (학번, 과목코드) 복합키인데, "이름"은 학번에만 종속되고 "과목명"은 과목코드에만 종속된다면 이는 부분 함수 종속으로 2NF 위반이다.
- **3NF 위반 예시**: "사원(사번, 부서코드, 부서명)"에서 사번→부서코드→부서명으로 이어지는 이행 종속이 있다면 3NF 위반이다(부서명을 알려면 부서코드를 거쳐야 함).
- **이상 현상(Anomaly) 종류**: 삽입 이상, 삭제 이상, 갱신 이상 (위 예시 참고)
- **함수 종속(Functional Dependency)**: 속성 X 값이 정해지면 속성 Y 값이 유일하게 결정될 때 "X → Y" 로 표기하며, 정규화 판단의 핵심 기준이 된다.
- **반정규화(De-normalization)**: 조회 성능 향상을 위해 의도적으로 중복을 허용하는 기법(테이블 통합, 컬럼 중복, 파생 컬럼 추가, 수직/수평 파티셔닝 등). 트랜잭션이 많은 OLTP 환경보다는 조회가 많은 시스템(리포팅, 통계)에서 고려한다.

### 4-3. 키(Key)의 종류

| 키 | 설명 |
| --- | --- |
| 슈퍼키(Super Key) | 유일성만 만족(최소성은 없어도 됨) |
| 후보키(Candidate Key) | 유일성 + 최소성 만족 |
| 기본키(Primary Key) | 후보키 중 선택된 대표 키, NULL 불가 |
| 대체키(Alternate Key) | 기본키로 선택되지 않은 후보키 |
| 외래키(Foreign Key) | 다른 테이블의 기본키를 참조하는 속성, 참조 무결성 유지 |
| 복합키(Composite Key) | 두 개 이상의 속성을 조합해 유일성을 만족시키는 키 |

**예시**: "수강(학번, 과목코드, 성적)" 테이블에서 (학번, 과목코드)의 조합만 유일성을 보장한다면 이것이 후보키이자 기본키(복합키)가 된다. 학번 하나만으로는 유일성이 보장되지 않는다(한 학생이 여러 과목을 수강하므로).

### 4-4. SQL 핵심 문법

DDL(데이터 정의어): CREATE, ALTER, DROP, RENAME, TRUNCATE — 테이블/스키마 구조 자체를 정의
DML(데이터 조작어): SELECT, INSERT, UPDATE, DELETE — 데이터 자체를 조작
DCL(데이터 제어어): GRANT, REVOKE, COMMIT, ROLLBACK — 권한 부여/회수, 트랜잭션 확정/취소

```sql
-- 테이블 생성 예시 (DDL)
CREATE TABLE employee (
    emp_id INT PRIMARY KEY,
    emp_name VARCHAR(50) NOT NULL,
    dept_id INT,
    salary INT,
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
);

-- JOIN 예시
SELECT A.emp_name, B.dept_name
FROM employee A
INNER JOIN department B ON A.dept_id = B.dept_id
WHERE A.salary > 3000
GROUP BY B.dept_name
HAVING COUNT(*) > 2
ORDER BY B.dept_name DESC;

-- 서브쿼리 예시
SELECT emp_name
FROM employee
WHERE salary > (SELECT AVG(salary) FROM employee);
```

- **WHERE vs HAVING**: WHERE는 그룹화 이전 행 필터링, HAVING은 그룹화 이후 집계 결과 필터링. 예를 들어 "급여 3000 이상인 사람만" 필터링은 WHERE를, "부서별 인원이 2명 이상인 부서만" 필터링은 HAVING을 사용한다.
- **JOIN 종류**: INNER JOIN(양쪽 모두 조건을 만족하는 교집합), LEFT/RIGHT OUTER JOIN(한쪽 기준 전체 + 매칭되는 상대 데이터, 매칭 없으면 NULL), FULL OUTER JOIN(양쪽 전체), CROSS JOIN(카티션 곱, 모든 조합), SELF JOIN(자기 자신과 조인, 예: 사원-사원의 상사 관계 조회)
- **집합 연산자**: UNION(합집합, 중복 제거), UNION ALL(합집합, 중복 포함, 성능이 더 좋음), INTERSECT(교집합), MINUS/EXCEPT(차집합)
- **뷰(View)**: 하나 이상의 테이블에서 유도된 가상 테이블, 실제 데이터를 저장하지 않고 쿼리 결과만 보여줌. 보안(특정 컬럼 은닉)과 재사용성 확보에 유용
- **저장 프로시저(Stored Procedure)**: DB 서버에 미리 저장해둔 SQL 로직 묶음, 반복 실행되는 복잡한 로직을 캡슐화해 네트워크 통신 비용도 줄임
- **트리거(Trigger)**: 특정 이벤트(INSERT/UPDATE/DELETE) 발생 시 자동으로 실행되는 프로시저, 데이터 무결성 유지나 로그 기록에 사용

### 4-5. 트랜잭션과 무결성

- **트랜잭션 특성 ACID**: 원자성(Atomicity, 전부 실행되거나 전부 취소), 일관성(Consistency, 실행 전후 DB 상태가 일관됨), 고립성(Isolation, 동시 실행 트랜잭션이 서로 간섭하지 않음), 지속성(Durability, 커밋된 결과는 영구 반영)
- **무결성 제약조건**: 개체 무결성(기본키는 NULL 불가·중복 불가), 참조 무결성(외래키는 참조 테이블에 존재해야 함), 도메인 무결성(속성 값은 정의된 도메인 범위 내여야 함)
- **회복 기법**: 로그 기반 회복(REDO/UNDO — 장애 발생 시 로그를 보고 커밋된 트랜잭션은 재실행(REDO), 커밋 안 된 트랜잭션은 취소(UNDO)), 체크포인트(일정 시점 상태 기록으로 회복 시간 단축), 그림자 페이징(변경 전 페이지를 별도 보관)
- **동시성 제어**: 로킹(Locking, 공유 락(읽기용, 여러 트랜잭션 동시 가능)/배타 락(쓰기용, 하나의 트랜잭션만 가능)으로 자원 접근 제어), 타임스탬프 순서(트랜잭션 시작 시각 기준으로 순서 결정), 낙관적 동시성 제어(충돌이 드물다고 가정하고 커밋 시점에만 검사)

**동시성 제어가 필요한 이유 — Lost Update 예시**: 두 트랜잭션이 동시에 같은 계좌 잔액(1000원)을 읽고 각각 잔액을 갱신한다고 하자.

```text
T1: 잔액 읽기(1000) → 입금 100 계산(1100) → 저장
T2: 잔액 읽기(1000) → 출금 200 계산(800) → 저장
```

만약 T1과 T2가 순서 보장 없이 동시에 실행되면, 나중에 저장하는 트랜잭션이 먼저 저장된 값을 덮어써서 결과가 1100이나 800 중 하나만 반영되고 다른 하나는 사라진다(Lost Update, 갱신 손실 문제). 이를 막기 위해 락(Lock)으로 한 트랜잭션이 끝날 때까지 다른 트랜잭션의 접근을 차단하는 것이 동시성 제어의 핵심 목적이다.

- **트랜잭션 격리 수준**: Read Uncommitted < Read Committed < Repeatable Read < Serializable 순으로 격리 수준이 높아지며, 격리 수준이 높을수록 동시성(성능)은 떨어지고 일관성은 높아진다.
- **분산 데이터베이스**: 여러 지역에 물리적으로 분산된 데이터베이스를 하나의 논리적 데이터베이스처럼 사용, 위치 투명성·중복 투명성·병행 투명성·장애 투명성을 목표로 함

### 4-6. 인덱스

- **클러스터드 인덱스**: 데이터 물리적 정렬 순서와 인덱스 순서 일치, 테이블당 1개만 생성 가능(책의 "가나다순 본문 정렬"에 비유 가능)
- **논클러스터드 인덱스**: 별도 구조로 주소만 저장, 여러 개 생성 가능하지만 클러스터드 인덱스보다 조회 성능은 다소 낮음(책 뒤의 "찾아보기 색인"에 비유 가능)
- 인덱스는 조회(SELECT) 성능을 높이지만 INSERT/UPDATE/DELETE 시 인덱스도 함께 갱신해야 하므로 오버헤드가 발생한다. 따라서 조회가 잦고 변경이 적은 컬럼에 생성하는 것이 유리하다.
- **인덱스 자료구조**: 대부분의 DBMS는 B-Tree/B+Tree 기반 인덱스를 사용(범위 검색에 강함), 해시 인덱스는 등가 비교(=)에 특화

## 5. 4과목: 프로그래밍 언어 활용

### 5-1. C언어 핵심 문법

```c
#include <stdio.h>
int main() {
    int arr[3] = {1, 2, 3};
    int *p = arr;
    printf("%d\n", *(p + 1)); // arr[1] = 2 출력, 포인터 연산
    printf("%d\n", *p + 1);   // arr[0]+1 = 1+1 = 2, 결과는 같지만 의미가 다름
    p++;
    printf("%d\n", *p);       // 포인터가 다음 칸을 가리키므로 arr[1] = 2
    return 0;
}
```

이 예제에서 헷갈리기 쉬운 것이 `*(p + 1)`과 `*p + 1`의 차이다. `*(p + 1)`은 "포인터를 한 칸 이동한 뒤 그 값을 참조"하는 것이고, `*p + 1`은 "포인터가 가리키는 값에 1을 더하는 것"이다. 우연히 값이 같아 보여도 계산 순서와 의미는 완전히 다르므로 반드시 괄호 위치를 확인해야 한다.

- 포인터 연산, 배열과 포인터의 관계(배열명은 첫 원소의 주소를 의미하는 상수 포인터), 구조체(struct), 형변환(Type Casting)은 매년 출제
- 연산자 우선순위: `()` > 단항(`!`, `++`, `--`) > 산술(`*`,`/`,`%` > `+`,`-`) > 관계(`<`,`>`,`==`) > 논리(`&&`,`||`) > 대입(`=`)
- **기억 클래스(Storage Class)**: auto(지역변수 기본, 함수 종료 시 소멸), static(함수 종료 후에도 값 유지, 다음 호출 시 이전 값 이어감), extern(다른 파일의 전역변수 참조), register(레지스터에 저장 시도해 접근 속도 향상)
- **배열 vs 포인터 차이**: 배열은 크기가 고정되고 sizeof로 전체 크기를 알 수 있지만, 포인터는 주소값만 저장하며 sizeof 결과는 포인터 크기(보통 8바이트)로 고정된다.
- **비트 연산자**: `&`(AND), `|`(OR), `^`(XOR), `~`(NOT), `<<`(왼쪽 시프트, 2배 곱과 동일 효과), `>>`(오른쪽 시프트, 2배 나눔과 동일 효과) — 예를 들어 `5 << 1`은 이진수 `101`을 한 칸 왼쪽으로 밀어 `1010`(=10)이 된다. 결과값을 직접 계산하는 문제가 자주 출제된다.

### 5-2. Java 핵심 개념

- **객체지향 4대 특성**: 캡슐화(데이터와 메서드를 하나로 묶고 외부 접근 제한), 상속(부모 클래스의 특성을 재사용), 다형성(같은 이름의 메서드가 다르게 동작), 추상화(공통 특성을 뽑아 일반화)
- **접근 제어자**: public(모든 곳에서 접근 가능) > protected(같은 패키지+상속 관계) > default(같은 패키지, package-private) > private(같은 클래스 내부만)
- **오버로딩 vs 오버라이딩**: 오버로딩(Overloading)은 같은 이름·다른 매개변수(컴파일 타임 다형성 — 어떤 메서드가 호출될지 컴파일 시점에 결정), 오버라이딩(Overriding)은 부모 메서드를 자식이 동일한 시그니처로 재정의(런타임 다형성 — 실제 객체 타입에 따라 실행 시점에 결정)
- **예외 처리**: try-catch-finally 구문 사용, checked 예외(컴파일 시점에 처리 강제, IOException 등)와 unchecked 예외(런타임에 발생, NullPointerException 등)로 구분
- **인터페이스 vs 추상 클래스**: 인터페이스는 다중 상속(구현) 가능하고 모든 메서드가 기본적으로 추상 메서드, 추상 클래스는 단일 상속만 가능하지만 일반 메서드도 포함 가능

```java
class Animal {
    void sound() { System.out.println("동물 소리"); }
}
class Dog extends Animal {
    @Override
    void sound() { System.out.println("멍멍"); } // 오버라이딩: 부모 메서드를 재정의
}
class Calculator {
    int add(int a, int b) { return a + b; }
    double add(double a, double b) { return a + b; } // 오버로딩: 매개변수 타입으로 구분
}

public class Main {
    public static void main(String[] args) {
        Animal a = new Dog();   // 부모 타입 변수에 자식 객체 대입(다형성)
        a.sound();               // 실제 객체(Dog)의 sound()가 호출되어 "멍멍" 출력
        try {
            int result = 10 / 0; // ArithmeticException 발생
        } catch (ArithmeticException e) {
            System.out.println("0으로 나눌 수 없음");
        } finally {
            System.out.println("항상 실행됨");
        }
    }
}
```

위 코드에서 `Animal a = new Dog();`처럼 부모 타입 변수에 자식 객체를 담는 것을 업캐스팅이라 하며, 이때 `a.sound()`를 호출하면 컴파일 시점 타입(Animal)이 아니라 실제 객체 타입(Dog)의 메서드가 실행된다는 점이 다형성의 핵심이다.

### 5-3. Python 핵심 문법

```python
# 리스트 컴프리헨션과 슬라이싱은 자주 출제
nums = [1, 2, 3, 4, 5]
squares = [n**2 for n in nums if n % 2 == 0]
print(squares)  # [4, 16]  (2와 4의 제곱만 계산됨)
print(nums[1:3])  # [2, 3]  (인덱스 1부터 3 직전까지)
print(nums[::-1])  # [5, 4, 3, 2, 1] 역순 슬라이싱

# 딕셔너리와 튜플 언패킹
person = {"name": "홍길동", "age": 20}
for key, value in person.items():
    print(key, value)

# 함수와 가변 인자
def total(*args, **kwargs):
    print(sum(args))       # 위치 인자들의 합
    print(kwargs)           # 키워드 인자들을 딕셔너리로 받음

total(1, 2, 3, x=10, y=20)  # 6 출력 후 {'x': 10, 'y': 20} 출력
```

- 동적 타이핑(변수 선언 시 타입을 명시하지 않음, 실행 중 타입이 결정됨), 들여쓰기 기반 블록 구조(중괄호 대신 콜론+들여쓰기로 블록을 구분), 가변(list, dict, set — 생성 후 내용 변경 가능)/불변(tuple, str, int — 한 번 생성되면 내용 변경 불가) 자료형 구분
- **함수 정의와 기본 인자**: `def func(a, b=10):` 형태로 기본값 지정 가능, `*args`(가변 위치 인자, 튜플로 받음), `**kwargs`(가변 키워드 인자, 딕셔너리로 받음)
- **람다식**: `lambda x, y: x + y` 형태의 익명 함수, `map`/`filter`/`sorted`의 key 인자 등과 함께 자주 출제. 예: `sorted(nums, key=lambda x: -x)`는 내림차순 정렬.

### 5-4. 운영체제 핵심 개념

#### 프로세스 스케줄링 알고리즘

| 알고리즘 | 특징 |
| --- | --- |
| FCFS | 도착 순서대로 처리, 구현 단순, 대기시간 편차 큼(호위 효과 발생 — 긴 작업 뒤에 짧은 작업이 오래 기다림) |
| SJF | 실행시간 짧은 작업 우선, 평균 대기시간 최소이나 기아 현상 가능(긴 작업이 계속 밀림) |
| SRT | SJF의 선점형 버전, 남은 실행시간이 더 짧은 프로세스가 도착하면 선점 |
| 라운드 로빈(RR) | 시간 할당량(Time Quantum)마다 순환, 선점형, 응답시간 우수하나 문맥 교환 비용 존재 |
| 우선순위 | 우선순위 높은 작업 먼저, 기아 현상 방지 위해 에이징(Aging)으로 대기 프로세스의 우선순위를 점진적으로 상승 |
| 다단계 큐 | 프로세스를 우선순위별로 여러 큐에 분리 배치, 큐 간 이동 불가 |
| 다단계 피드백 큐 | 다단계 큐 + 큐 간 이동 허용, 실행시간에 따라 큐를 옮겨 CPU/IO 바운드 프로세스를 구분 |

**FCFS 평균 대기시간 계산 예제**: 프로세스가 다음과 같이 도착했다고 하자(모두 0시점에 도착했다고 가정).

| 프로세스 | 실행시간 |
| --- | --- |
| P1 | 5 |
| P2 | 3 |
| P3 | 8 |

FCFS는 도착 순서(P1→P2→P3)대로 실행되므로:

```text
P1: 0~5 실행 (대기시간 0)
P2: 5~8 실행 (대기시간 5, P1이 끝날 때까지 기다림)
P3: 8~16 실행 (대기시간 8, P1+P2가 끝날 때까지 기다림)

평균 대기시간 = (0 + 5 + 8) / 3 = 4.33
```

만약 SJF로 실행하면 실행시간이 짧은 순서(P2→P1→P3)로 처리되어:

```text
P2: 0~3 실행 (대기시간 0)
P1: 3~8 실행 (대기시간 3)
P3: 8~16 실행 (대기시간 8)

평균 대기시간 = (0 + 3 + 8) / 3 = 3.67
```

이렇게 SJF가 FCFS보다 평균 대기시간이 짧다는 것을 직접 계산해보면, 왜 SJF가 "평균 대기시간 최소"라는 특징을 갖는지 체감할 수 있다.

- **프로세스 상태 전이**: 생성(New) → 준비(Ready) → 실행(Running) → 대기(Waiting/Blocked) → 종료(Terminated), Ready와 Running 사이는 디스패치/타임아웃으로 순환
- **교착상태(Deadlock) 발생 4대 조건**: 상호 배제(자원을 한 프로세스만 독점), 점유와 대기(자원을 가진 채 다른 자원을 기다림), 비선점(자원을 강제로 뺏을 수 없음), 순환 대기(프로세스들이 원형으로 자원을 기다림) — 넷 다 성립해야 교착상태가 발생한다.
- **교착상태 해결책**: 예방(Prevention, 4대 조건 중 하나를 제거), 회피(Avoidance, 은행원 알고리즘으로 안전 상태 유지), 발견(Detection, 자원 할당 그래프로 사이클 탐지), 회복(Recovery, 프로세스 종료 또는 자원 선점)
- **메모리 관리**: 페이징(고정 크기 블록, 외부 단편화 없음), 세그멘테이션(가변 크기, 의미 단위 분할이지만 외부 단편화 발생 가능), 페이지 교체 알고리즘(FIFO, LRU-최근 최소 사용, LFU-최소 빈도 사용, Optimal-이론상 최적)
- **가상 메모리와 스와핑**: 물리 메모리보다 큰 프로그램을 실행하기 위해 디스크를 보조 기억장치처럼 활용, 페이지 폴트가 과도하게 발생하면 스래싱(Thrashing) 현상 발생

### 5-5. 네트워크 기초

- **OSI 7계층**: 물리(전기 신호) - 데이터링크(MAC, 프레임) - 네트워크(IP, 라우팅) - 전송(TCP/UDP, 포트) - 세션(연결 관리) - 표현(인코딩/암호화) - 응용(HTTP, FTP 등) (암기: 물데네전세표응)
- **계층별 대표 장비/프로토콜**: 물리(허브, 리피터), 데이터링크(스위치, 브리지, ARP), 네트워크(라우터, IP, ICMP), 전송(TCP, UDP), 응용(HTTP, FTP, SMTP, DNS)
- **TCP vs UDP**: TCP는 연결 지향·신뢰성 보장(3-way handshake로 연결 수립, 흐름 제어·혼잡 제어 포함), UDP는 비연결형·빠른 전송(신뢰성은 낮지만 오버헤드가 적어 스트리밍·DNS에 사용)
- **3-way handshake**: SYN → SYN+ACK → ACK 순서로 연결을 수립하며, 종료 시에는 4-way handshake(FIN 교환)를 사용

**서브네팅 계산 예제**: `192.168.1.100/26` 주소가 주어졌을 때 네트워크 주소와 브로드캐스트 주소를 직접 구해보자.

```text
1. /26은 서브넷 마스크가 255.255.255.192(11111111.11111111.11111111.11000000)를 의미
2. 호스트 비트가 6비트 남으므로 한 서브넷의 크기는 2^6 = 64개 주소
3. 192.168.1.0 ~ 192.168.1.63, 192.168.1.64 ~ 192.168.1.127 ... 순으로 64개씩 구간이 나뉨
4. 100은 두 번째 구간(64~127)에 속하므로:
   - 네트워크 주소 = 192.168.1.64
   - 브로드캐스트 주소 = 192.168.1.127
   - 사용 가능한 호스트 = 192.168.1.65 ~ 192.168.1.126 (총 62개, 네트워크/브로드캐스트 주소 제외)
```

- **IP 주소 클래스**: A(0~127, 대규모 네트워크), B(128~191, 중규모), C(192~223, 소규모) — 시험에서 서브넷 마스크로 네트워크 주소/브로드캐스트 주소 계산 문제 출제 빈도 높음
- **주요 프로토콜**: DHCP(IP 자동 할당), DNS(도메인-IP 변환), ARP(IP-MAC 변환), NAT(사설 IP-공인 IP 변환)

### 6-1. 소프트웨어 개발 방법론

| 방법론 | 특징 |
| --- | --- |
| 폭포수 모델(Waterfall) | 순차적 진행, 요구사항 변경 어려움, 문서화 중심, 각 단계 완료 후 다음 단계로 이동 |
| 프로토타입 모델 | 시제품을 먼저 만들어 요구사항 정제, 사용자 피드백을 초기에 반영 |
| 나선형 모델(Spiral) | 위험 분석을 반복하며 점진적으로 개발, 대형·고위험 프로젝트에 적합하나 관리 복잡 |

- **애자일 선언문 핵심 가치**: 공정·도구보다 개인과 상호작용을, 포괄적 문서보다 동작하는 소프트웨어를, 계약 협상보다 고객과의 협력을, 계획 준수보다 변화 대응을 더 가치 있게 여긴다 — 시험에서 "애자일이 중요하게 여기는 것"을 묻는 문제의 근거가 되는 원칙이다.
- **애자일 방법론 종류**: 스크럼(Scrum, 스프린트 단위 반복 개발+데일리 미팅), XP(eXtreme Programming, 실천 방법 중심), 칸반(Kanban, 시각화 보드로 작업 흐름 관리)
- **XP의 핵심 실천 방법**: 짝 프로그래밍(Pair Programming, 두 사람이 함께 코딩해 품질 향상), 지속적 통합(CI, 자주 병합해 충돌 최소화), 테스트 주도 개발(TDD, 테스트 코드를 먼저 작성), 리팩토링, 소규모 릴리즈
- **스크럼 구성 요소**: 제품 백로그(요구사항 목록), 스프린트 백로그(이번 스프린트 작업), 스프린트(보통 2~4주 단위 반복), 일일 스크럼 회의, 스프린트 리뷰/회고
- **정보공학 방법론**: 데이터 중심으로 계획-분석-설계-구축 단계를 거치는 전통적 방법론, ERD와 데이터 흐름도(DFD)를 중심으로 진행
- **컴포넌트 기반 개발(CBD)**: 재사용 가능한 컴포넌트를 조립해 시스템을 구축, 개발 기간 단축과 품질 향상이 목적

### 6-2. 프로젝트 관리 기법

- **CPM(임계경로기법, Critical Path Method)**: 프로젝트 전체 기간을 결정하는 가장 긴 경로(여유시간=0인 작업들의 경로) 산출, 이 경로의 작업이 지연되면 전체 프로젝트가 지연됨
- **PERT(Program Evaluation and Review Technique)**: 확률적 기법으로 낙관치·최빈치(중간치)·비관치를 이용해 예상 소요 시간을 산정.

**PERT 기대 시간 계산 예제**: 어떤 작업의 낙관치(최선의 경우)가 2일, 최빈치(가장 가능성 높은 경우)가 4일, 비관치(최악의 경우)가 6일이라면:

```text
기대 시간(TE) = (낙관치 + 4 × 최빈치 + 비관치) / 6
             = (2 + 4×4 + 6) / 6
             = (2 + 16 + 6) / 6
             = 24 / 6
             = 4일
```

이 공식은 최빈치에 4배의 가중치를 줘서 "가장 일어날 법한 시나리오"를 중심으로 기대값을 계산하는 방식이다.

- **WBS(Work Breakdown Structure)**: 작업을 계층적으로 분할해 관리, 프로젝트 범위를 명확히 하고 일정·비용 산정의 기초가 됨
- **간트 차트(Gantt Chart)**: 작업별 일정을 막대 그래프로 표현, 작업 간 시간적 관계를 직관적으로 파악 가능하지만 작업 간 의존 관계 표현은 CPM/PERT보다 약함
- **소프트웨어 규모 산정 기법**: LOC(코드 라인 수 기반, 간단하지만 부정확), FP(기능 점수, Function Point — 기능 단위로 규모 산정, 언어에 무관하게 측정 가능), COCOMO(LOC 기반 비용 산정 모델, 유기적(소규모·단순)/반분리형(중간 규모)/내장형(대규모·복잡, 하드웨어 제약 존재) 3가지 프로젝트 유형으로 구분)

### 6-4. 보안

- **암호화 방식**: 대칭키(DES, AES — 암복호화 키가 동일, 속도 빠르지만 키 교환·관리가 어려움), 비대칭키(RSA — 공개키로 암호화·개인키로 복호화, 키 교환 문제는 해결되지만 속도 느림)
- **해시 함수**: SHA-256, MD5(현재는 충돌 취약점으로 사용 지양) — 무결성 검증용, 단방향이라 복호화 불가능
- **접근 통제 모델**: DAC(임의적 접근 통제, 소유자가 권한 설정), MAC(강제적 접근 통제, 시스템이 보안 등급으로 통제), RBAC(역할 기반 접근 통제, 역할에 권한을 부여)
- **보안 공격 유형과 대응**: SQL 삽입(입력값에 SQL 구문을 주입 → 대응: 입력값 검증·Prepared Statement 사용), XSS(악성 스크립트 삽입 → 대응: 출력값 이스케이프 처리), CSRF(사용자 권한을 도용해 요청 위조 → 대응: CSRF 토큰 검증), DDoS(다수 시스템으로 서비스 마비 → 대응: 트래픽 필터링·CDN 분산), 스니핑(패킷 도청 → 대응: 암호화 통신), 스푸핑(출처 위장 → 대응: 인증 강화), 랜섬웨어(파일 암호화 후 금전 요구 → 대응: 정기 백업)
- **네트워크 보안 장비**: 방화벽(Firewall, 정해진 규칙으로 트래픽 차단/허용), IDS(침입 탐지 시스템, 탐지만 수행), IPS(침입 방지 시스템, 탐지+차단까지 수행)
- **시큐어 코딩**: 입력 데이터 검증(SQL 삽입·XSS 방지), 보안 기능(적절한 인증/암호화 사용), 시간 및 상태(경쟁 조건·레이스 컨디션 방지), 에러 처리(민감 정보가 담긴 에러 메시지 노출 금지), 캡슐화(중요 데이터 은닉)
- **인증 기술**: 지식 기반(비밀번호), 소유 기반(OTP, 보안카드), 생체 기반(지문, 홍채), 다중 인증(MFA, 2가지 이상 결합)

### 6-5. IT 프로젝트 관련 표준/용어

- **ISO/IEC 25010**: 소프트웨어 품질 특성(기능 적합성, 성능 효율성, 호환성, 사용성, 신뢰성, 보안성, 유지보수성, 이식성) — 8대 품질 특성을 묻는 문제가 자주 출제된다.
- **CMMI(Capability Maturity Model Integration)**: 소프트웨어 프로세스 성숙도 모델(5단계: 초기 → 관리 → 정의 → 정량적 관리 → 최적화), 조직의 프로세스 역량을 평가하는 기준
- **SLA(Service Level Agreement)**: 서비스 수준 협약, 서비스 제공자와 사용자 간 성능·가용성 목표를 명문화한 계약
- **ISO/IEC 12207**: 소프트웨어 생명주기 프로세스에 대한 국제 표준
- **소프트웨어 3권**: 저작권(창작물 보호), 특허권(기술적 발명 보호), 산업재산권 — IT 지식재산권 문제에서 함께 출제되는 경우가 있다.

## 7. 시험 직전 최종 체크리스트

과목별로 스스로에게 물어보고, 막히는 부분이 있으면 해당 섹션으로 돌아가 다시 확인하자.

### 1과목(소프트웨어 설계)

- [ ] 기능적/비기능적 요구사항을 예문만 보고 즉시 구분할 수 있는가
- [ ] 응집도/결합도 강약 순서를 헷갈리지 않고 말할 수 있는가
- [ ] GoF 디자인 패턴 3분류(생성/구조/행위)와 대표 패턴을 매칭할 수 있는가
- [ ] 클래스 다이어그램의 집합(Aggregation)과 합성(Composition) 차이를 예시로 설명할 수 있는가

### 2과목(소프트웨어 개발)

- [ ] 트리 그림을 보고 전위/중위/후위 순회 결과를 직접 써낼 수 있는가
- [ ] 정렬 알고리즘별 평균/최선/최악 시간 복잡도를 표 없이 말할 수 있는가
- [ ] 화이트박스/블랙박스 테스트 기법을 각각 3개 이상 댈 수 있는가

### 3과목(데이터베이스 구축)

- [ ] 정규화 1NF~BCNF 조건을 예시 테이블과 함께 설명할 수 있는가
- [ ] JOIN 종류별 결과 차이(INNER vs OUTER)를 그림으로 그릴 수 있는가
- [ ] ACID 4가지 특성을 각각 한 문장으로 설명할 수 있는가

### 4과목(프로그래밍 언어 활용)

- [ ] C 포인터 연산 `*(p+1)`과 `*p+1`의 차이를 설명할 수 있는가
- [ ] 스케줄링 알고리즘별 평균 대기시간을 직접 계산할 수 있는가
- [ ] 서브넷 마스크로 네트워크/브로드캐스트 주소를 계산할 수 있는가
- [ ] 교착상태 4대 조건을 순서대로 암기했는가

### 5과목(정보시스템 구축관리)

- [ ] PERT 기대 시간 공식을 이용해 직접 계산할 수 있는가
- [ ] 최신 IT 용어(디지털 트윈, 엣지 컴퓨팅, RPA 등) 정의를 한 줄로 설명할 수 있는가
- [ ] 보안 공격 유형별 대응 방안을 하나씩 짝지어 말할 수 있는가

### 공통

- [ ] 최근 3개년 기출문제를 최소 2회독 이상 했는가
- [ ] 오답노트에 정리한 "함정 포인트"를 시험 직전에 다시 훑었는가

정보처리기사 필기는 범위가 넓어 보이지만, 실제 출제 문항은 매 회차 유사한 패턴으로 반복되는 경우가 많다. 이 글에서 다룬 개념 설명, 계산 예제, 트레이싱 과정을 손으로 직접 한 번씩 따라 해보고, 그 다음 기출문제를 풀면서 취약한 부분만 다시 이 글로 돌아와 확인하는 방식이 가장 효율적이다. 특히 3과목(데이터베이스)과 5과목(정보시스템 구축관리)은 암기량 대비 점수 획득이 쉬운 과목이므로 우선순위를 두고 학습하는 것을 추천한다.
